Informational INFO-IBKR-001 — IBKR API roles (roster vs prices)

API Role Meaning
Scanner API
reqScannerData / TOP_PERC_GAIN, etc.		 Ranked-roster delivery “Keep this table's membership current during its update window.” Delivery is a persistent reqScannerSubscription owned by ibkr/scanner_stream.py (ADR 008) — not repeated one-shot polling, and it is not a price stream.
Market data API
reqMktData, depth, tick-by-tick		 Continuous subscription “Send me updates for these symbols.” This is the live price path.

Mental model: scanner = roster; market data = scoreboard. During a table's update window, scanner batches replace its roster and L1 updates displayed values. At the table boundary, its snapshot freezes; HOD-owned L1 remains a separate concern.

API What it does Concrete example When to use When not to use
reqScannerSubscription Long-lived scanner subscription. Slot stays open; IB can push an updated ranked list until you cancel. Counts as 1 of 10 concurrent scanner slots. Returns contracts/ranks only — no live prices. At 12:00 you subscribe to TOP_PERC_GAIN and leave it open. At 12:00 IB sends ranks 1–50. At 12:03 RBNE jumps onto the list — IB can push a new ranked list while the subscription is still alive. You do not call again to learn the roster changed. At 12:00:10 RBNE enters the top 50 — Nova does not hear about it until the next one-shot (e.g. ~20s later). Periodic roster refresh (Nova’s usual gainers/losers/seeds pattern) Not for real-time quotes; don’t spam (pacing / load)

When you no longer need that live roster Nothing to cancel if you only used one-shot reqScannerDataAsync
reqScannerParameters Asks IB for the catalog of available scanner codes and filters (XML). Meta/discovery, not market data. On a tooling day you call this once and get XML listing codes like TOP_PERC_GAIN, HOT_BY_VOLUME, and filter tags (price/volume/etc.). Nova calls reqMktData(XYZ). At 12:01:05 last=$5.80; at 12:01:06 last=$5.91 — UI/HOD see those ticks as they arrive. Live prices for Gainers rows / HOD active set / open ticker Don’t stream thousands of symbols; limited by market-data lines
cancelMktData Stops the L1 stream for a symbol and frees that market-data line. RBNE was in the HOD active set with a live L1 stream. It drops out of the active 40 → Nova cancels mkt data for RBNE → ticks stop; line free for the next admitted symbol. Leave active set / close ticker / rotate explore slots Don’t cancel while you still need live prices for that symbol
reqTickersAsync (ib_async) One-shot snapshot quotes for a batch of contracts. Waits until IB finishes the snapshot (often ~11s), then returns fields once — not a stream. Cold path: you have 20 new symbols from a scanner and don’t want 20 full L1 streams yet. You call reqTickersAsync on those 20; ~11s later you get one price/prevClose/volume bundle each to paint the table. Seconds 12–30: no more updates from that call unless you ask again (or switch those names to reqMktData). Cold / discovery backfill when a full stream isn’t worth it Not the live table freshness SLA (too slow / not continuous)
reqMktDepth / depth stream Level-2 order book for one symbol. Streaming bid/ask levels until cancelled. You open ticker RBNE in Stock View. Nova requests depth for RBNE only. reqTickByTickData (AllLast) Time & sales: every print (last trade) for one symbol until cancelled. RBNE is open. Nova subscribes AllLast for RBNE. Tape shows 12:01:05 100@5.90, 12:01:06 500@5.91, … Closing the ticker (or switching symbol) cancels that tape; you don’t run AllLast on all 50 gainers. Open ticker Time & Sales Not for 50 gainers at once
reqHistoricalData Pulls historical bars (e.g. 1-min OHLCV) for a window. One response set per request; subject to historical pacing. RBNE just joined the HOD watch set mid-move. Live ticks alone have an empty 5-min surge buffer. Nova asks for the last ~15 one-minute bars, seeds the price buffer, then Squeeze can compute “up 5% in 5 min.” Charts use the same family of calls for candle history. Surge seed / charts / session-high from bars Heavy pacing — small batches only (Nova caps seeds/tick)
qualifyContractsAsync Resolves a symbol string into a full IB contract (conId, exchange, etc.) before other requests. Scanner returned symbol RBNE. Before reqMktData, Nova qualifies Stock(“RBNE”,“SMART”,“USD”) → gets conId / details. Later ticks reuse that qualified contract; you don’t re-qualify RBNE on every price tick. Before streaming, snapshots, or historical for a new symbol Don’t re-qualify the same symbols every tick

Informational INFO-IBKR-004 — ScannerSubscription is a filter object, not a list

ScannerSubscription (instrument, locationCode, scanCode, abovePrice, …) is a request/criteria object you build once. It is not itself a list, and there is no separate "list" that reqScannerDataAsync iterates over. You hand that same criteria object to one of two delivery modes:

Delivery mode What happens
reqScannerData / reqScannerDataAsync Send the criteria once → get one ranked list back → request finished.
reqScannerSubscription Send the criteria once → subscription stays open → IB pushes updated ranked lists until cancelled.

reqScannerDataAsync is just the coroutine wrapper for reqScannerData — same one-shot API, not a third option.

Informational INFO-IBKR-005 — Current one-shot lifecycle vs target table-window subscription

Current backend/ibkr/discovery.py::_one_shot_scanner() opens reqScannerSubscription, waits for the first completed batch, then always cancels it. That safe cancellation fixed scanner-slot leaks, but the overall behavior is still one-shot. The target keeps only the session-owned scanner subscription open for its table update window and cancels it exactly at the freeze boundary.

Scanning (either delivery mode) and Level-1 streaming are unrelated APIs: the scanner returns symbol names/ranks only, never prices. Nova's L1 (live prices for the HOD active set / open ticker) runs through reqMktData in backend/ibkr/scanner_l1.py — completely separate from the scanner call.

Target pipeline: session-owned scanner subscription → roster snapshot → table-window L1 patches; after freeze, separate HOD-owned reqMktData may continue for admitted symbols without mutating the completed table.

Informational INFO-IBKR-006 — What a scan code like TOP_PERC_GAIN actually is

Not a number and not a data container. scanCode is a string identifier that selects a pre-built ranking formula running server-side inside Gateway/TWS. Passing it in does not store or hold anything — IBKR returns a ranked list of contracts shaped by that formula (no price fields; those come from a separate quote/L1 call).

Scan code Ranking formula (server-side)
TOP_PERC_GAINBiggest intraday % gain: (price − prior close) / prior close, descending
TOP_PERC_LOSEBiggest intraday % loss
TOP_OPEN_PERC_GAINBiggest gap: today's open vs prior close
HOT_BY_VOLUMEHighest volume activity
MOST_ACTIVEMost active by trade count/volume
