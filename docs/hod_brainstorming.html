Informational INFO-IBKR-001 — IBKR API roles (roster vs prices)

API Role Meaning
Scanner API
reqScannerData / TOP_PERC_GAIN, etc.		 Periodic snapshot “Give me the current ranked list.” It is not a price stream.
Market data API
reqMktData, depth, tick-by-tick		 Continuous subscription “Send me updates for these symbols.” This is the live price path.

Mental model: scanner = roster (who is on Top Gainers); market data = scoreboard (live prices). Nova’s gainer_cache holds the last scanner snapshot; L1 streaming updates prices for subscribed symbols.

Informational INFO-IBKR-002 — Scanner scan codes Nova uses today

Mostly one-shot reqScannerDataAsync pulls (not 10 long-lived reqScannerSubscription slots held open). Each scan code returns ≤50 symbols. IBKR allows up to 10 concurrent open scanner subscriptions.

Scan code Purpose Where it feeds
TOP_PERC_GAIN Top Gainers gainer_cache (+ HOD seeds)
TOP_PERC_LOSE Top Losers loser_cache
TOP_OPEN_PERC_GAIN Gappers (open vs prior close) gapper_cache
TOP_AFTER_HOURS_PERC_GAIN AH gainers After Hours tab
TOP_AFTER_HOURS_PERC_LOSE AH losers After Hours tab
HOT_BY_VOLUME Volume heat HOD seed / watch pool
TOP_VOLUME_RATE Volume rate HOD seed / watch pool
MOST_ACTIVE Most active HOD seed / watch pool
TOP_PERC_GAIN + belowPrice=20 Sub-$20 gainers HOD seed head (so mega-gainers don’t crowd out cheap runners)

Resolved 2026-07-23: HOD eligibility = TOP_PERC_GAIN → gainer_cache only (REQ-HOD-001). The volume/activity scan codes above (HOT_BY_VOLUME, TOP_VOLUME_RATE, MOST_ACTIVE) are excluded per REQ-HOD-003; TOP_OPEN_PERC_GAIN (Gappers) is excluded per REQ-HOD-002.

Informational INFO-IBKR-003 — Which IBKR API to use, and when (with examples)

API What it does Concrete example When to use When not to use
reqScannerSubscription Long-lived scanner subscription. Slot stays open; IB can push an updated ranked list until you cancel. Counts as 1 of 10 concurrent scanner slots. Returns contracts/ranks only — no live prices. At 12:00 you subscribe to TOP_PERC_GAIN and leave it open. At 12:00 IB sends ranks 1–50. At 12:03 RBNE jumps onto the list — IB can push a new ranked list while the subscription is still alive. You do not call again to learn the roster changed. Cancel when you no longer want that live roster. Always-on Top Gainers (or other scan) when you want roster push updates Not for streaming prices; don’t hold more than 10 open
reqScannerData / reqScannerDataAsync One-shot scanner. Ask once → get current ranked list → that request is finished. No ongoing push for that call. Returns contracts/ranks only (≤50) — no live prices. At 12:00:00 Nova asks “TOP_PERC_GAIN, max 50”. IB returns e.g. XYZ #1, ABC #2, … once. Nova writes gainer_cache; that call is done. At 12:00:10 RBNE enters the top 50 — Nova does not hear about it until the next one-shot (e.g. ~20s later). Prices for names already on the list still update via reqMktData, not via this scanner call. Periodic roster refresh (Nova’s usual gainers/losers/seeds pattern) Not for real-time quotes; don’t spam (pacing / load)
cancelScannerSubscription Ends a long-lived scanner subscription and frees its slot among the max 10. You had an open TOP_PERC_GAIN subscription using scanner slot #3. You call cancel for that reqId → IB stops pushing gainer-list updates; slot #3 is free for e.g. HOT_BY_VOLUME. When you no longer need that live roster Nothing to cancel if you only used one-shot reqScannerDataAsync
reqScannerParameters Asks IB for the catalog of available scanner codes and filters (XML). Meta/discovery, not market data. On a tooling day you call this once and get XML listing codes like TOP_PERC_GAIN, HOT_BY_VOLUME, and filter tags (price/volume/etc.). You use that to know what you can subscribe to — you do not get today’s gainer symbols from this call. Discovery / docs / tooling; rare at runtime Not part of the trading-day HOD hot path
reqMktData Level-1 stream for one symbol. Continuous ticks (last, bid/ask, volume, day high tick-6, etc.) until cancelled. Uses a market-data line, not a scanner slot. XYZ is on gainer_cache. Nova calls reqMktData(XYZ). At 12:01:05 last=$5.80; at 12:01:06 last=$5.91 — UI/HOD see those ticks as they arrive. The Gainers roster still only changes on the next scanner shot/subscription update; this call is the live price path. Live prices for Gainers rows / HOD active set / open ticker Don’t stream thousands of symbols; limited by market-data lines
cancelMktData Stops the L1 stream for a symbol and frees that market-data line. RBNE was in the HOD active set with a live L1 stream. It drops out of the active 40 → Nova cancels mkt data for RBNE → ticks stop; line free for the next admitted symbol. Leave active set / close ticker / rotate explore slots Don’t cancel while you still need live prices for that symbol
reqTickersAsync (ib_async) One-shot snapshot quotes for a batch of contracts. Waits until IB finishes the snapshot (often ~11s), then returns fields once — not a stream. Cold path: you have 20 new symbols from a scanner and don’t want 20 full L1 streams yet. You call reqTickersAsync on those 20; ~11s later you get one price/prevClose/volume bundle each to paint the table. Seconds 12–30: no more updates from that call unless you ask again (or switch those names to reqMktData). Cold / discovery backfill when a full stream isn’t worth it Not the live table freshness SLA (too slow / not continuous)
reqMktDepth / depth stream Level-2 order book for one symbol. Streaming bid/ask levels until cancelled. You open ticker RBNE in Stock View. Nova requests depth for RBNE only. Book shows bid 5.90×800 / ask 5.91×1200 and updates as the book changes. The other 49 gainers do not get depth — only the focused symbol. Open ticker depth panel Not for the whole Gainers list
reqTickByTickData (AllLast) Time & sales: every print (last trade) for one symbol until cancelled. RBNE is open. Nova subscribes AllLast for RBNE. Tape shows 12:01:05 100@5.90, 12:01:06 500@5.91, … Closing the ticker (or switching symbol) cancels that tape; you don’t run AllLast on all 50 gainers. Open ticker Time & Sales Not for 50 gainers at once
reqHistoricalData Pulls historical bars (e.g. 1-min OHLCV) for a window. One response set per request; subject to historical pacing. RBNE just joined the HOD watch set mid-move. Live ticks alone have an empty 5-min surge buffer. Nova asks for the last ~15 one-minute bars, seeds the price buffer, then Squeeze can compute “up 5% in 5 min.” Charts use the same family of calls for candle history. Surge seed / charts / session-high from bars Heavy pacing — small batches only (Nova caps seeds/tick)
qualifyContractsAsync Resolves a symbol string into a full IB contract (conId, exchange, etc.) before other requests. Scanner returned symbol RBNE. Before reqMktData, Nova qualifies Stock(“RBNE”,“SMART”,“USD”) → gets conId / details. Later ticks reuse that qualified contract; you don’t re-qualify RBNE on every price tick. Before streaming, snapshots, or historical for a new symbol Don’t re-qualify the same symbols every tick

Rule of thumb: (1) who’s on the list → scanner · (2) live price → reqMktData · (3) book / tape / bars → only for focused symbols.

Informational INFO-IBKR-004 — ScannerSubscription is a filter object, not a list

ScannerSubscription (instrument, locationCode, scanCode, abovePrice, …) is a request/criteria object you build once. It is not itself a list, and there is no separate "list" that reqScannerDataAsync iterates over. You hand that same criteria object to one of two delivery modes:

Delivery mode What happens
reqScannerData / reqScannerDataAsync Send the criteria once → get one ranked list back → request finished.
reqScannerSubscription Send the criteria once → subscription stays open → IB pushes updated ranked lists until cancelled.

reqScannerDataAsync is just the coroutine wrapper for reqScannerData — same one-shot API, not a third option.

Informational INFO-IBKR-005 — Nova only uses the one-shot scanner; L1 is a separate API

Confirmed by repo search: backend/ibkr/discovery.py calls ib.reqScannerDataAsync(sub) only. reqScannerSubscription has zero uses anywhere in Nova today.

Scanning (either delivery mode) and Level-1 streaming are unrelated APIs: the scanner returns symbol names/ranks only, never prices. Nova's L1 (live prices for the HOD active set / open ticker) runs through reqMktData in backend/ibkr/scanner_l1.py — completely separate from the scanner call.

Pipeline: one-shot scanner → roster (gainer_cache / loser_cache) → reqMktData → live prices for admitted symbols only.

Informational INFO-IBKR-006 — What a scan code like TOP_PERC_GAIN actually is

Not a number and not a data container. scanCode is a string identifier that selects a pre-built ranking formula running server-side inside Gateway/TWS. Passing it in does not store or hold anything — IBKR returns a ranked list of contracts shaped by that formula (no price fields; those come from a separate quote/L1 call).

Scan code Ranking formula (server-side)
TOP_PERC_GAINBiggest intraday % gain: (price − prior close) / prior close, descending
TOP_PERC_LOSEBiggest intraday % loss
TOP_OPEN_PERC_GAINBiggest gap: today's open vs prior close
HOT_BY_VOLUMEHighest volume activity
MOST_ACTIVEMost active by trade count/volume

Informational INFO-IBKR-008 — what HOD_MOMO_ACTIVE_SET_CAPACITY = 40 actually caps

This is not a display limit — it has nothing to do with how many rows/alerts show in the HOD Momo UI (today_alerts is unbounded and separately virtualized). It caps how many symbols get a live IBKR reqMktData feed at once for HOD evaluation, because IBKR limits total concurrent market-data lines per API connection.

Budget lineSlotsPurpose
Active scanner tab≤50Whatever mover table is currently open in the UI
HOD active set40HOD evaluation pool (HOD_MOMO_ACTIVE_SET_CAPACITY)
Reserve5Open ticker / depth panel headroom
IBKR_L1_STREAM_BUDGET100Total concurrent market-data lines Nova budgets

The 40 (and its mover_slots/seed_slots/explore_slots quota-arbitration logic) exists because 5 competing sources (gainers/gappers/losers/AH/seeds) needed a fair-share mechanism. Once eligibility is Gainers-only (REQ-HOD-001/002/003) — itself IBKR-capped at 50 rows — that arbitration problem mostly disappears. Flagged for simplification when REQ-HOD-001 is implemented; not decided/changed here.
